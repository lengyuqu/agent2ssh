# Repository Guidelines

## Project Structure & Module Organization

Agent2SSH combines a React/Vite desktop frontend with a Rust/Tauri backend. Frontend code lives in `src/`, with reusable UI in `src/components/`, shared types in `src/types.ts`, API helpers in `src/api.ts`, and styling/tokens in `src/index.css` plus `src/components/ui/`. Rust code is under `src-tauri/src/`; binaries are in `src-tauri/src/bin/` for the CLI, daemon, and MCP server. Rust integration tests live in `src-tauri/tests/`. Documentation is in `docs/`, `README.md`, and `CHANGELOG.md`. Helper scripts are in `scripts/`; bundled skill instructions are in `skills/agent2ssh/SKILL.md`.

## Build, Test, and Development Commands

- `npm install`: install frontend and Tauri dependencies.
- `npm run dev`: run the Vite frontend.
- `npm run build`: type-check and build the frontend.
- `npm test`: run frontend behavior tests with Vitest (jsdom + Testing Library).
- `npm run test:watch`: run frontend tests in watch mode.
- `npm run tauri:dev`: launch the desktop app in development mode.
- `npm run tauri:build`: build sidecar binaries, frontend, and the packaged Tauri app.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --lib`: run Rust library tests.
- `cargo test --manifest-path src-tauri/Cargo.toml --lib`: run Rust library tests for the default (tauri) feature set. This is the only command that compiles and runs `src/tauri_commands.rs` tests, so run it alongside the `--no-default-features` one. It needs the frontend `dist/` to exist, so run `npm run build` first. It also compiles `build.rs` with the tauri feature, where `tauri_build::build()` requires every `bundle.externalBin` sidecar to already exist as `src-tauri/binaries/<name>-<host-triple>` — build them and run `./scripts/prepare-sidecars.sh`, or blank the check out with `TAURI_CONFIG='{"bundle":{"externalBin":[]}}'` when you only want to lint or unit-test the library. Without either, the build script aborts with `resource path binaries/agent2ssh-cli-<triple> doesn't exist`. The same `build.rs` also delay-loads `comctl32` on Windows: the tauri feature imports `comctl32!TaskDialogIndirect`, which exists only in the v6 side-by-side assembly, and test binaries get no manifest — the loader bound System32's 5.82 copy and the run died before `main` with `0xc0000139` (STATUS_ENTRYPOINT_NOT_FOUND). Delay-loading resolves it on first call instead, which a test never makes.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --test cli_smoke`: run CLI/MCP smoke tests.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --test connect_deadline`: run the connect-deadline regressions (a peer that accepts TCP and then goes silent must not leak a blocked worker). Binds its own loopback listener, so it needs no fixture.
- `cargo check --manifest-path src-tauri/Cargo.toml --no-default-features --bin agent2ssh --bin agent2ssh-mcp`: CLI/MCP compile check (no features).
- `cargo check --manifest-path src-tauri/Cargo.toml --no-default-features --features daemon --bin agent2ssh-daemon`: daemon compile check.
- `cargo check --manifest-path src-tauri/Cargo.toml`: Tauri app compile check (default feature). Same sidecar prerequisite as `cargo test --lib` above.
- **Windows builds compile OpenSSL from source, so they need two extra tools.** `src-tauri/Cargo.toml` enables `ssh2`'s `openssl-on-win32` together with `vendored-openssl`, which makes the Windows binary self-contained (nothing to ship alongside it) and gives it curve25519, ed25519/ECDSA host keys, AES-GCM and the OpenSSH private-key container parser — a WinCNG build has none of those, which is why it could not handshake with OpenSSH 10.0+. `openssl-src` drives that build with `nmake` (from the MSVC toolchain) and a **full** Perl for OpenSSL's `Configure`. `src-tauri/.cargo/config.toml` pins `OPENSSL_SRC_PERL` to `scripts/win-perl.cmd`, which resolves one and explains itself when it cannot, because the Perl bundled with Git for Windows is trimmed and fails with `Can't locate Locale/Maketext/Simple.pm in @INC` — an error that names no fix. Install it with `scoop install perl`. NASM is optional and only enables OpenSSL's assembly routines (`scoop install nasm`; `openssl-src` silently falls back to `no-asm` without it). The first build after either changes takes roughly 12 minutes; later ones reuse it.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --features daemon --test daemon_integration`: run daemon integration tests. It drives a **mirrored** router, not the daemon binary — see Testing Guidelines.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --test local_exec`: run the local exec target tests (named environments, process-tree reclamation, truncation, recursion guard). Needs no fixture and no SSH: the "server" is this machine.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --features daemon --test daemon_local_exec_e2e`: run the `/local-exec` end-to-end tests against a real `agent2ssh-daemon` process, including establishing a Visual Studio developer shell. Requires the `daemon` feature, because the file uses `env!("CARGO_BIN_EXE_agent2ssh-daemon")`.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --features daemon --test daemon_resident_session_e2e`: run the `/resident-sessions` end-to-end tests against a real daemon (lifecycle, shell-state persistence across execs, the start-then-collect read, the guards). Needs no Windows: the default `local` environment is a plain stdin-reading shell.
- `cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --test container_terminal_manual -- --ignored --nocapture`: real-machine container-terminal verification (Docker and Apple container discovery + a real Terminal.app launch). `#[ignore]`d because the tests open real windows; start a probe container first (`docker run -d --name a2s-probe alpine:latest sleep 3600`).
- `AGENT2SSH_TEST_SSH_PORT=2222 cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --test exec_fixture -- --test-threads=1`: run the sshd fixture tests (skipped without the env var). Also run by `./scripts/e2e-container.sh` and by the CI `real-ssh-e2e` job, which supply `AGENT2SSH_TEST_SSH_KEY`. Build a local server with `docker build -t a2s-sshd:local scripts/sshd-fixture && docker run -d --name a2s-sshd -p 2222:22 a2s-sshd:local` (swap `docker` for the runtime you use — `wslc`, or Apple's `container`).
- `./scripts/e2e-container.sh`: run the containerized real-SSH E2E (real exec, SFTP round-trips, resume, exec-fixture suite). The runtime is resolved by `agent2ssh containers runtime` — Docker, wslc or Apple container — so it is not Docker-only. `scripts/e2e-docker.sh` remains a compatibility shim for the old name. The client key is generated by `agent2ssh keys generate`, so the run also proves that a key this app produces is a key it can authenticate with; `AGENT2SSH_E2E_IMAGE` selects the sshd image; the default is a current release (OpenSSH 10.3 at the time of writing) and works on every platform this project builds, because the Windows build links OpenSSL. Pin `lscr.io/linuxserver/openssh-server:9.9_p2-r0-ls198` only to test a WinCNG build, which shares no key-exchange algorithm with OpenSSH 10.0+.
- `agent2ssh containers list [--all] [--runtime <id>] [--json]`: list container exec targets across Docker, wslc, Apple container and Kubernetes. `agent2ssh containers runtime [--json|--binary]`: show (or print just the path of) the local runtime the app drives.
- `agent2ssh keys algorithm [--name|--json]`: print the key algorithm this build can authenticate with (a property of the linked libssh2, not of the host OS; every platform this project builds now links OpenSSL and therefore answers `ed25519`). `agent2ssh keys generate <name> [--type ed25519|rsa] [--json]`: generate a pair into `~/.agent2ssh/keys/`, printing the private key path alone so it can be fed to `--key`.
- `./scripts/e2e-local.sh`: run local preflight builds, tests, smoke checks, and sidecar preparation.

## Coding Style & Naming Conventions

Use TypeScript with React function components and PascalCase component filenames, such as `HostList.tsx`. Keep helpers and modules in lower camel case. Rust uses the 2021 edition, snake_case modules, and focused files by capability, such as `policy.rs`, `session.rs`, and `daemon_control.rs`. Run `cargo fmt --manifest-path src-tauri/Cargo.toml` before Rust changes. Keep UI copy aligned with `src/i18n.tsx`. Exec, SFTP, terminal, persistent sessions, jump-host proxying, connection retention, and port forwarding use the embedded SSH transport, so document backend changes carefully — exec is the exception, because it has a second target: see Execution Targets below.

## Execution Targets

An exec request names its target through `host`, and which kind it is decides both who authorizes it and whether it can prompt.

- **SSH host.** `host` is a configured profile alias, resolved by `resolve_host` and run by the embedded SSH transport. This is what `host` means in `/exec`, `/exec-multi`, `/exec/compare`, `/exec/preview` and `/exec/stream` — all five, without exception.
- **Local environment.** `host` is `local`, or `local:<environment>` for a named one. `types::is_local_host` recognises it (case-sensitively, so an SSH alias spelled `Local:vs` remains a host) and `local_exec::LocalEnvironment` resolves it; the selectable set is `pwsh`, `cmd`, `gitbash`, `vs` (a Visual Studio developer shell) and `wsl[:<distribution>]` — see `resolve_environment`, `find_vs_dev_shell_script` and the `Wsl` variant. Adding one means a variant plus a `resolve_*` arm, because an environment is only data: a program, plus an optional prelude that runs in the same shell before the command. `/local-exec` is its daemon route, deliberately separate from `/exec` so `host` keeps one meaning in the four multi-host handlers.

Two rules keep the local target from becoming a weaker path than the SSH one:

- **Authorization is shared, not parallel.** The daemon's `local_exec` handler calls the same `preflight_guarded_request` as `/exec` — gate, limits, scope, risk, approval. `tests/daemon_integration.rs` asserts that from the source text, together with the ordering that makes it worth anything: the local-host check must run *before* the gate chain, or scope and approval would be evaluated against an alias the client typed rather than against the target that actually runs. That test has to be updated whenever the handler's shape changes; it fails loudly rather than silently passing.
- **Only the daemon can prompt.** The CLI, MCP and desktop entry points authorize through `authorize_command_without_approval_handler`, whose approval closure only writes a rejection, so an approval policy there is a hard block rather than a card. Anything that needs a real approval must go through the daemon.

Container *interactive* terminal launch is **not** an exec target: `container_discovery` and `container_terminal` are a separate discovery-and-launch path that validates argv and nothing else — no scope, risk, approval or audit. But *capture* exec inside a container is one: `host = local:<runtime>:<container-id>` (e.g. `local:docker:abc123`, runtime one of `docker`, `wslc`, `apple`) rides the `/local-exec` envelope — same gate, scope, risk, approval, audit — and runs the runtime CLI's non-TTY exec (`exec <id> /bin/sh -c <cmd>`; no `-i`, no `-t`, and a request carrying `stdin` is refused rather than dropped). `container_runtime::exec_args` (`exec -it`) remains the interactive shape only; `exec_capture_args` is the capture shape.

A **resident session** keeps one of those shell environments alive across commands (`resident_session.rs`, daemon routes under `/resident-sessions`): the shell is spawned once and warmed (its prelude — e.g. the Visual Studio bootstrap — runs at open), then commands are written to its stdin and demarcated by a per-command sentinel carrying a nonce and the exit code. Three rules hold. Every command, and the open itself, goes through `preflight_guarded_request` keyed on the session's own `local:<id>` host — a resident command is never a weaker path than a one-shot exec (pinned by `resident_session_routes_run_the_shared_preflight` in `tests/daemon_integration.rs`, including the ordering that the session's host id is read from the registry *before* the gate chain). A command that outlives its timeout kills the whole session — a shell without a console cannot be interrupted, so honesty beats a fake resume. And the session *state* is daemon-owned: every surface — MCP `resident_session_*`, CLI `agent2ssh resident open|exec|close|list`, the desktop panel — is a thin client over these routes, because a non-daemon surface cannot run the approval flow; there is deliberately no process-local fallback. `GET /resident-sessions/{id}` is the start-then-collect read: it reports the session's rolling buffer (the *same* buffer exec consumes — no second capture path), consumes nothing, counts no idle activity, and reports `dead` for a shell that exited on its own. One-shot `/local-exec` stays the default; a session is what an agent opts into when shell state persisting across commands is the point.

**Resident sessions and local exec — verification status.** The portability split in this section is closed. MCP tools `local_exec` + `resident_session_open/exec/close` (tool count `71→75`, `docs/skills.md` moved with it), CLI `agent2ssh local exec` and `agent2ssh resident open|exec|close|list`, the `GET /resident-sessions/{id}` read endpoint (with its api.yaml entry), the real-daemon e2e (`tests/daemon_resident_session_e2e.rs`, 6 tests), the desktop resident-sessions panel, and the Windows-only evidence below — all recorded on Windows 11 (VS BuildTools 18, WSL2 Ubuntu) on 2026-09-28:

- `local:vs` warm start: `open` pays the Visual Studio bootstrap once (`warmup_ms ≈ 2.6–2.8 s`), then every `where.exe cl` resolves `…\VS\18\BuildTools\VC\Tools\MSVC\…\cl.exe` at ~100–120 ms per command rather than ~2.6 s. The *flat* latency is the "prelude ran once" evidence: the warm read consumes the sentinel line, so the sentinel cannot be counted in the buffer afterwards. Differential pair: the same command exits 1 ("could not find files") under `local:cmd` — the environment, not luck, is what puts `cl` on `PATH`.
- `local:cmd` resident integration: `tests/resident_session.rs` covers `cd`/`set` persistence, `%ERRORLEVEL%` reporting and the echoed-frame skip against a real `cmd /D /Q` session.
- `local:wsl:Ubuntu` warm start: `warmup_ms ≈ 0.3–0.9 s`, execs at 20 ms, `cd`/`export` persist, `echo $$` returns the same pid twice (one shell, not a respawn per command), and a failing command reports its own code without killing the session. Hot end-to-end ~0.21 s against ~0.58 s for the same command through one-shot `local:wsl:Ubuntu`.
- Desktop panel at runtime: driven through the WebView2 CDP endpoint against a live daemon — the panel renders the session list (host, id, label, idle time) and its close button moves the daemon from two sessions to one.

Two machine prerequisites the first run tripped over, both environment-side and worth checking before blaming the code:

- A WSL distribution has to finish its OOBE first. One whose first-run provisioning never completed (e.g. `wsl --install` interrupted at the username prompt) prints `Provisioning the new WSL instance …` on every start without a command, so the resident warm-up waits out `OPEN_TIMEOUT_SECS = 120` and the session is reported dead with that line in its buffer. Set `[user] default=<name>` in `/etc/wsl.conf`, drop the `[oobe]` block from `/etc/wsl-distribution.conf`, then `wsl --terminate <distro>` — not `wsl --shutdown`, which also stops Docker Desktop's distro.
- `tauri dev` copies `src-tauri/binaries/<name>-<host-triple>` over `target/debug/<name>.exe`, so a stale sidecar silently becomes the daemon the app and a hand-run CLI talk to. The symptom is a *new route answering 404* while the source plainly has it: check the artifact (`strings target/debug/<name>.exe | grep -c <route>`), rebuild the sidecars (`cargo build --release …` then `./scripts/prepare-sidecars.sh`), or run the freshly built binary from outside the target directory.

## Testing Guidelines

Place Rust integration tests in `src-tauri/tests/` and name them by behavior or surface, for example `cli_smoke.rs` or `daemon_integration.rs`. Prefer targeted tests for policy, risk, approval, daemon, and command execution changes. Tests behind `#[cfg(feature = "tauri")]` — such as the ones in `src/tauri_commands.rs` — only compile under the default feature set, so Rust changes need both `cargo test --no-default-features --lib` and `cargo test --lib`. Any test that needs a real SSH server should follow `tests/exec_fixture.rs`: skip unless `AGENT2SSH_TEST_SSH_PORT` is set, and wire it into `scripts/e2e-container.sh` so CI runs it. Two patterns need no server at all. `tests/local_exec.rs` runs real commands on this machine against an isolated config dir; it pins `AGENT2SSH_LOCAL_SHELL` and is `#[serial]`, because the config dir, the shell override and the recursion guard are all process-global. `tests/daemon_local_exec_e2e.rs` spawns the real daemon binary (`env!("CARGO_BIN_EXE_agent2ssh-daemon")`, hence its crate-level `#![cfg(feature = "daemon")]`), seeds `<config_dir>/daemon.token` before starting it (the loader keeps an existing non-empty token, so the test knows it without racing the daemon to the file), probes the token-free `/health` route for readiness, and passes the environment to the child instead of mutating its own — which is what lets those tests run in parallel. Reaching for a real daemon is worth it here: `daemon_integration.rs` runs a *mirrored* router with its own handlers, so nothing in it exercises the real handler code.

Three habits this suite has already paid for. Assert the **reason**, not just the status code — a 400 also comes from failing to resolve a host, so a status-only assertion keeps passing after the guard it was written for is gone. When a guard exists in two layers (an outer check plus a defensive copy), the response cannot reveal whether the outer one survived, so pin the *ordering* with a source-text assertion. And prove a source-parsing guard can actually fail by mutating the code in a way that still compiles — point a route at another handler, or insert a comment between a function name and its `(` so the literal disappears. A fourth habit is platform honesty: a test that needs a Windows-only artifact (`local:cmd`, the VS shell) picks a named environment the *host* has for the shared assertion and keeps the Windows-only discriminator behind `cfg!(windows)` — see the named-environment tests in `tests/local_exec.rs` and `tests/daemon_local_exec_e2e.rs`.

Two contract tests parse sources rather than calling code, and both have to be satisfied in the same change: `api_yaml_documents_every_daemon_route` requires every `.route(...)` in the daemon to appear under `paths:` in `docs/api.yaml`, and rejects phantom entries; `mcp_tool_list_contains_exactly_75_tools` together with `mcp_tools_match_skills_md_documentation` requires the MCP registry, its hard-coded tool count and `docs/skills.md` to move as one. Frontend behavior tests live next to components as `src/**/*.test.{ts,tsx}` (for example `src/components/HostList.test.tsx` and `src/nav.test.ts`) and run with `npm test` (Vitest + jsdom + Testing Library, configured in `vite.config.ts` with setup in `src/test-setup.ts`); mock `src/api.ts` in tests so they never touch the Tauri bridge. For frontend changes, run `npm test` and `npm run build`; add manual desktop checks with `npm run tauri:dev` when UI behavior changes.

## Commit & Pull Request Guidelines

Recent commits use short, imperative, sentence-case messages, for example `Add desktop daemon lifecycle controls` and `Document R5 regression retest`. Keep commits scoped to one behavior or documentation update. Pull requests should explain the change, list validation commands, link related issues or reports, and include screenshots for desktop UI changes.

## Security & Configuration Tips

Local runtime data is stored under `~/.agent2ssh/`, including daemon tokens and policy files. Do not commit secrets, host keys, private SSH config, or generated local tokens. For policy and storage details, update `docs/guides/configuration-guide.md` alongside behavior changes.
