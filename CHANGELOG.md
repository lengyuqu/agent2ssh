# Changelog

All notable changes to Agent2SSH are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- **Desktop cloud download and restore**: saved WebDAV settings now support encrypted backup downloads and confirmed restoration even with automatic upload disabled. Recovery validates the complete snapshot before writes, preserves local credentials and trust, creates an undo snapshot, rolls back partial failures, and refreshes hosts and proxies. Uploads and recovery are serialized; downloads are capped at 20 MiB including chunked responses.
- **SSH user-certificate authentication, `host add --passphrase`, and a connection-mode matrix**: a host whose `key_path` has an OpenSSH certificate next to it (`<key>-cert.pub`, what `ssh-keygen -s` writes) now offers the certificate instead of the bare key, so servers that only trust a CA (`TrustedUserCAKeys`) accept it; before, the key alone was sent and the server answered `Username/PublicKey combination invalid`. No new host field: the file name is the convention OpenSSH itself uses. `agent2ssh host add --passphrase` stores an encrypted key's passphrase through the credential store like `--password` already did. `scripts/e2e-ssh-matrix.sh` runs password, wrong password, key, unauthorized key, encrypted key with the right and wrong passphrase, and certificate (right principal, wrong principal, expired) against OpenSSH 8.3, 8.8, 9.3, 9.9 and 10.3 and Dropbear in containers, on Docker or Apple container; it also covers ed25519, RSA-3072, ECDSA P-256/384/521 keys (OpenSSH and PEM containers) as plain keys, encrypted keys and certificates, ssh-agent identities, a 1 MiB SFTP round trip, and a legacy-algorithm server. All pass on Docker. Dropbear has no certificate support and is skipped for that mode.
- **Readiness check and explicit start for Apple `container`**: the runtime is a CLI over an `apiserver` that must be started with `container system start`, and every command — `list` included — fails opaquely while it is down, so discovery silently returned nothing and the `container_discovery` test failed on any host where the CLI was installed but the service was not. `ContainerRuntime::service_running` probes `container system status` (5 s cap), discovery now names a stopped service and the command that starts it, and `containers runtime --json` / the `container_runtimes` command report `service_running` and `start_command`. Starting stays explicit: `agent2ssh containers start [--runtime apple]`, or opt in to starting on demand with `AGENT2SSH_CONTAINER_AUTOSTART=1`. Docker and wslc have no service to probe and are unaffected. Covered with a fake `container` script rather than the host's real service.
- **The local-execution surfaces an agent can call now exist end to end: `local_exec` and the resident-session trio are MCP tools, CLI subcommands, a daemon read endpoint, a real-daemon e2e and a desktop panel.** This closes the portable half of the resident-session outstanding list in AGENTS.md — the half any development host can do — leaving only the Windows verification evidence. The four MCP tools (`local_exec`, `resident_session_open`, `resident_session_exec`, `resident_session_close`; registry, gate tests and `docs/skills.md` move 71 → 75 together) are deliberately daemon-only: the daemon is what can run a high-risk command through an approval prompt, so instead of a process-local fallback arm like the PTY session tools have, a call with no daemon running fails with an error that names what to start. The CLI mirrors them as `agent2ssh local exec` and `agent2ssh resident open|exec|close|list` — thin `remote_config` clients that default to the daemon on this machine and honour the global `--daemon <alias>` flag; `print_daemon_exec_result` passes the command's exit code through as the process exit code so scripts can branch on it. The new `GET /resident-sessions/{id}` read endpoint serves start-then-collect workflows: a command backgrounded inside the shell (`(sleep 1; ...) &`) keeps writing into the session's own rolling buffer after the exec POST has returned with its sentinel, and the read — which consumes nothing, counts no activity, and sits behind the bearer token but outside the execution gate, like listing — reports it together with `truncated`/`dropped_bytes`; it also reports `dead` for a shell that exited on its own, so a collector can stop polling before the idle reaper runs. `resident_get_core` is the one new lib function, and it reads the *same* `SessionBuffer` exec reads — there is no second capture path to keep consistent. The desktop panel (Resident Sessions module) lists the daemon's sessions read-only with a close action, and states what the feature is when the list is empty rather than rendering silence. Real-daemon evidence: `tests/daemon_resident_session_e2e.rs` (6 tests, driving the actual binary over HTTP — lifecycle incl. post-close 400 with the reason, exported-variable persistence across two execs, the detached-command read, the non-local-host guard's reason, 401 on both routes, unknown-session refusal) passes on this Mac, the default `local` environment being a plain stdin-reading shell. The Windows-only verification evidence this entry ended on has since landed — see the Verified entries below, which also record the four Windows bugs it turned up.
- **Resident environment sessions — an environment established once, commanded many times**: `resident_session.rs` keeps a long-lived shell for a `local:<id>` environment alive inside the daemon, so the cost of *establishing* the environment is paid at open instead of per command — the Visual Studio developer shell's bootstrap, roughly seven seconds before `cl.exe` runs, lands in the open and every later command starts warm, with the shell's own state (cwd, variables) persisting across commands. The mechanism is a sentinel protocol: each command is written to the shell's stdin followed by a line the session appends — `__A2S_DONE_<nonce>:<exit-code>` — whose nonce is generated per command and written after the command text, so a command cannot forge its own completion; the exec loop reads the session's rolling head+tail buffer until that exact marker appears, and everything before it is the output. The framing was measured against the real binaries rather than assumed: `pwsh -Command -` executes statements incrementally while stdin stays open (the property the whole design rests on), `cmd` echoes each command line back before running it, which the exit-code parse skips because `%ERRORLEVEL%` is not a number until cmd expands it, and the PowerShell command is deliberately not wrapped in a scriptblock because `& { $x = 1 }` would scope the assignment away and quietly break the state persistence the feature exists for. The policy is deliberately boring: the open, and every subsequent command, go through the same `preflight_guarded_request` as `/exec` and `/local-exec`, keyed on the session's own `local:<id>` host read from the registry rather than from the request, so a resident session can never become a weaker path than a one-shot exec — pinned by a source-level test (`resident_session_routes_run_the_shared_preflight`), mutation-verified twice. Two semantics differ honestly from `/local-exec` and are stated where the caller meets them: a command that outlives its timeout kills the whole session (a shell without a console cannot be interrupted, and long-running work belongs in a one-shot exec, which reaps its own process tree), and a command that exits the shell — `exit` is an authorized command that does what it says — kills the session too, reporting the shell's exit code. Daemon-only by design (one-shot `local:<id>` stays the default; shell state persisting is a semantic an agent must opt into), bounded by `AGENT2SSH_MAX_RESIDENT_SESSIONS` (default 8) and an idle TTL (`AGENT2SSH_RESIDENT_IDLE_TTL_SECS`, default 600, reaped by a daemon sweep), registered in the lifecycle registry, and reclaimed by a process-group kill on drop. Surfaces: `POST|GET /resident-sessions`, `POST /resident-sessions/{id}/exec`, `DELETE /resident-sessions/{id}` (containers are refused at open — they are one-shot exec targets — and `docs/api.yaml` documents all four). Tests: 12 unit (framing, sentinel parsing including cmd-echo skipping and chunk-boundary splits, rolling buffer) and 10 integration against real shells (state persistence differential, exit-code passthrough with `$LASTEXITCODE` reset so a cmdlet-only command reports none rather than a stale code, timeout kills session, `exit` kills session, close, list, refusal reasons).
- **The Windows build links OpenSSL, so it can complete a handshake with an OpenSSH 10.0+ server**: `src-tauri/Cargo.toml` enables `ssh2`'s `openssl-on-win32`, which is what makes `libssh2-sys`'s build script define `LIBSSH2_OPENSSL` and give up WinCNG. WinCNG offers MODP Diffie-Hellman only, and OpenSSH 10.0 removed every `diffie-hellman-group*` method, so a Windows client and a current server shared no key-exchange algorithm at all: the handshake died before authentication with `Session(-5) Unable to exchange encryption keys`, a message that points at nothing a user can act on and that no key conversion or server downgrade could fix. The same switch supplies curve25519, ed25519/ECDSA host keys, AES-GCM, `chacha20-poly1305` and the OpenSSH private-key container parser, so the preceding key-generation work is what now makes Windows the *less* constrained platform rather than the more constrained one. Three decisions are the substance of this change. First, `vendored-openssl` is enabled alongside `openssl-on-win32` rather than instead of it, and the two are not interchangeable: `libssh2-sys`'s build script tests the `CARGO_FEATURE_OPENSSL_ON_WIN32` environment variable and never inspects `vendored-openssl`, so with only the latter the build would compile an OpenSSL and still link WinCNG. Second, the dependency is scoped to `[target.'cfg(windows)'.dependencies]`, because `openssl-on-win32` activates `libssh2-sys`'s `cfg(windows)` `openssl-sys` dependency whereas on Linux and macOS an unconditional one would appear instead and demand a system OpenSSL — which is what leaves both Unix CI legs building exactly as before. Third, `vendored-openssl` rather than a linked local installation: linking the pre-built OpenSSL on this machine does work, but its `libssl.lib`/`libcrypto.lib` are *import* libraries, so the binary would load its crypto from a DLL and fail at startup on any machine lacking one. Compiling OpenSSL from source makes the binary genuinely self-contained — confirmed against the import table, which lists no `libssl*`/`libcrypto*` entry and only the system libraries OpenSSL 3.x itself needs — and removes any dependence on what a CI runner happens to have installed. That build needs `nmake` (from the MSVC toolchain) and a **full** Perl to drive OpenSSL's `Configure`; `src-tauri/.cargo/config.toml` pins `OPENSSL_SRC_PERL` to `scripts/win-perl.cmd`, a resolver that finds a complete distribution and names the fix when it cannot. The reason is narrow and worth stating: the Perl bundled with Git for Windows is trimmed, lacks `Locale::Maketext::Simple`, and — because Git Bash places its own `/usr/bin` ahead of every Windows PATH entry — is the one a bare `perl` resolves to *inside Git Bash only*, so the same build succeeded from PowerShell and failed from Git Bash on one machine. NASM is optional and merely enables OpenSSL's assembly routines; the CI Windows legs install it and run the resolver up front so the published artifacts are identical to a developer's rather than merely equivalent.
- **Key generation that produces a key this build can actually authenticate with**: `generate_key_core` generated Ed25519 and wrote it with `to_openssh()`, which made the keys the app hands a user unusable *twice over* on Windows — the WinCNG backend has no Ed25519 primitives at all (`wincng.c` references ed25519 zero times) and cannot read the OpenSSH private-key container it was written in. The only key that works there is RSA written as traditional PKCS#1 PEM, and nothing in the dependency tree could emit one: `ssh-key` generates RSA but writes the private half only as that same container, so the PEM encoder had to come from `rsa 0.9` plus `pkcs1`. It is pinned to 0.9 rather than the `rsa 0.10.0-rc.18` that `ssh-key` 0.7.0-rc.10 asks for, and its `rand_core` `getrandom` feature is deliberately left off so the crate keeps the single entropy source `keys.rs` already had. `generate_key_core_with` now takes a `KeyAlgorithm`, and `generate_key_core` resolves the default from the *build* rather than the host OS: Ed25519 where the OpenSSH container is readable, RSA-PEM where it is not, so enabling `ssh2`'s `openssl-on-win32` later flips the recommendation with no code change. RSA is generated at 3072 bits — the smallest size that reaches a 128-bit security level — and a smaller request is refused rather than silently honoured. Two details are the substance of this change. First, the entropy adapter: `RngCore::fill_bytes` cannot report an error, and neither quiet option is acceptable — leaving the buffer zeroed or untouched makes `num-bigint-dig`'s `gen_prime` loop forever, because it forces a fixed candidate (top two bits and the low bit set) and retries until *that same number* is prime, while a deterministic substitute risks emitting a key whose factors are recoverable — so a failed read records the reason and aborts, and `generate_rsa_pair` catches that and returns the recorded error. Second, the public-key line is encoded here rather than by `ssh-key`, whose `Mpint` belongs to a pre-release `ssh-encoding` this crate does not otherwise depend on; it is checked against `ssh-key`'s own parser in a unit test, against `ssh-keygen -l` and `openssl rsa -check` by hand, and against a real sshd in the E2E. The capability reaches the surfaces the app is scripted through, not only the desktop: `agent2ssh keys algorithm [--name|--json]`, `agent2ssh keys generate <name> [--type ed25519|rsa] [--json]` (whose default output is the private key path alone, so `--key "$(agent2ssh keys generate …)"` works), the `default_key_algorithm` Tauri command, and a type selector in the Keys panel that labels the recommendation, warns before generating a type this build cannot read, and sends an explicit type only when the user actually picks one. That last part is deliberate: when the recommendation is unknown the form sends no algorithm at all and lets the backend decide, so the two cannot disagree about which key was written.
- **Container discovery beyond Docker — wslc and Apple container**: The discovery module drove exactly one runtime, spelled out at every call site: the binary was `docker`, the list command was `docker ps --format {{json .}}`, and the JSON it parsed was docker's. `ContainerPlatform` gains `wslc` (the Windows Subsystem for Linux container CLI) and `apple` (Apple's `container`, macOS 26+ on Apple silicon), and the runtime-specific knowledge now lives in one table in `container_runtime.rs` — binary candidates, extra install directories, host support, list flags, exec argv and id prefix — instead of being implied by the code that used it. Three details were measured rather than assumed. First, `wslc` 2.9.13 emits **JSON-lines with docker's own keys** (`ID`/`Image`/`Names`/`Status`, plus `State`/`RunningFor`), verified against a real container created with `wslc create --name a2s-probe alpine:latest true`, so one parser covers Docker and wslc and the row fixtures in the tests are captured output rather than invented. Second, `wslc.exe` ships in `C:\Program Files\WSL`, which its installer does not add to `PATH`, so the runtime table carries a search directory the shared `path_resolver` fallbacks would not have found — on this machine that difference is the whole feature working or not. Third, Apple's `container list --format json` serializes `ManagedContainer`, a JSON *array* of `{id, configuration.image.reference, status.state}`, and its containers have no separate name field (`ManagedContainer.name` returns `configuration.id`), so the parser accepts both shapes and the discovered name is the id. A runtime that the host cannot run is reported as unsupported rather than as missing, and `select()` is strict when a caller names one: an explicitly requested runtime that is absent or unsupported is an error that says which, while auto-detection silently skips what is not installed so one broken runtime cannot hide another's containers. `AGENT2SSH_CONTAINER_RUNTIME` pins the choice for hosts where detection would pick wrong. Apple's path is the one thing not verified on real hardware — there is no Mac in this environment — so its dialect is a documented parse with tolerant field lookups and fixtures derived from the upstream struct definitions.
- **`agent2ssh containers`, and a desktop panel that uses it**: `container_discovery.rs` had been reachable only as the Tauri command `discover_containers`, which no component called — the feature existed in the backend and nowhere a user could see it. The CLI gains `containers list [--all] [--runtime <id>] [--json]` (an empty result names every runtime and its state, so "nothing running" is distinguishable from "nothing installed") and `containers runtime [--json | --binary]`, where `--binary` is the script-facing single-line output. The desktop gains a Containers module that lists each target with its runtime badge, image and status, copies the exec command, and opens it in the user's terminal. Launching is validated before it spawns: the binary must be one this process resolved itself (a known runtime or kubectl) and every argument must be a single token from the character set Docker, wslc and Apple all allow in container names, ids, namespaces and flags, so a renderer bug cannot turn the command into "run any binary with any arguments" and no quoting style has to be trusted anywhere. That check is deliberate about what it does not cover: a caller can still ask for a different container than discovery found, which is the authority the feature already grants by showing a copyable command.
- **Opt-in sshd fixture tests**: `src-tauri/tests/exec_fixture.rs` runs against a real sshd and covers the runtime behaviours the unit suites structurally cannot reach — draining stdout and stderr off one SSH channel, bounding a remote command by its timeout, and collecting a health snapshot, which shares that drain. The suite is skipped unless `AGENT2SSH_TEST_SSH_PORT` points at a reachable server; `scripts/sshd-fixture/Dockerfile` builds a throwaway alpine/OpenSSH container to point it at. The bugs below all passed the full unit, CLI and daemon suites before these tests existed.
- **Tauri feature coverage in CI**: A new `tauri-unit-tests` job compiles, lints and tests the default feature set, so `src/tauri_commands.rs` — behind `#[cfg(feature = "tauri")]` — can now fail a pull request. Every other cargo invocation in CI passes `--no-default-features`, which left that module uncompiled, untested and unlinted.
- **Exec fixture suite is no longer local-only**: It now also runs from `scripts/e2e-docker.sh`, and therefore from the `real-ssh-e2e` CI job, against the container that script already starts. It accepts `AGENT2SSH_TEST_SSH_KEY` for that key-only server.
- **Empty-target and zero-budget unit tests**: `exec_multi_core`, `exec_multi_with_strategy` and `preview_exec_multi` have tests pinning the `no hosts matched the requested hosts or tags` error, so the preview cannot drift back to reporting an empty plan as success. `BoundedCapture` gained boundary tests for a zero budget (keeps no bytes) and a one-byte budget (keeps the newest byte, since the odd byte is all tail).
- **Remote rename and delete on every surface**: `sftp_rename_core`, `sftp_remove_file_core`, `sftp_remove_dir_core` and `sftp_remove_dir_all_core` (the last a breadth-first recursive delete) were implemented and covered by `core.rs` tests, and `store.rs` already reserved classifier branches for the `sftp_rename` / `sftp_remove` action labels — but no CLI subcommand, MCP tool, daemon route, Tauri command or desktop control called them, so they were unreachable from every entry point. They are now wired end to end: `agent2ssh sftp rename|rm|rmdir|rm-rf`; the MCP tools `ssh_sftp_rename` / `ssh_sftp_rm` / `ssh_sftp_rmdir` / `ssh_sftp_rm_rf` (`tools/list` grows from 54 to 58 entries); `POST /sftp/rename|rm|rmdir|rm-rf` on the daemon; and the desktop commands `sftp_rename` / `sftp_remove_file` / `sftp_remove_dir` / `sftp_remove_dir_all`, surfaced as a right-click menu on remote rows in the SFTP panel. Every path reuses the existing operation gate, so the approval policy, risk override and audit behaviour are the same ones `sftp mkdir` already had.
- **`ssh-keygen -R` equivalent for the system OpenSSH `known_hosts`**: G13 shipped a one-way import — `import_known_hosts_from_ssh` parses OpenSSH's `~/.ssh/known_hosts` into the app store, exposed as `import_known_hosts`, `agent2ssh known-hosts import` and `api.importKnownHosts`. Its design note then concluded that the reverse direction was impossible, because a trusted-host record keeps only a SHA256 fingerprint and no public key. That reasoning holds for *writing* new entries but says nothing about *deleting* existing ones, so `remove_system_known_host` — the `ssh-keygen -R` equivalent — sat in `embedded_ssh.rs` with no caller anywhere in the repository. It now reaches both surfaces the import half already had: the desktop command `forget_system_known_host` backs a per-host "Forget in OpenSSH known_hosts" action in Host Management, and `agent2ssh known-hosts forget <host> [--port N] [--json]` completes the CLI, whose `KnownHostsCommands` enum had carried a lone `Import` variant since G13. `forget` matches the bare-hostname and `[host]:port` forms, rewrites the file in place leaving a `.bak`, leaves hashed entries and unrelated aliases alone, and prints a notice rather than failing when nothing matched — the same contract `ssh-keygen -R` has. Export (writing entries) remains unimplemented and, as the note says, unimplementable from a fingerprint-only store.
- **Editable SSH algorithm preferences**: `ssh_algo::save_algo_prefs` wrote `ssh_algos.json` and `embedded_ssh` read it before every handshake, but nothing in the application could write the file — it was a hand-edit-only setting documented nowhere, so the reader and the writer disagreed about whether the feature existed. Settings now has an "SSH algorithms" section whose dialog edits all eight lists (key exchange, host keys, ciphers, MACs and compression, each direction), shows which values diverge from the built-in defaults, and reverts in one click. Changes take effect on the next connection, because `load_algo_prefs()` is read per handshake; already-open sessions keep the algorithms they negotiated.
- **Editable redaction rules**: The A24 lifecycle in `redaction.rs` — seed `redact_rules.json` on first run, load it thereafter, reset on demand — was written, covered by five passing tests, and called by nobody, because the live redaction path (`store::redact_sensitive_text`, and behind it every audit record, webhook notification, playbook result and diagnostic export) called `redact_default` unconditionally. Editing the file changed nothing: the green tests showed the functions worked, not that the feature existed. That path now reads the file, so `redact_rules.json` is the source of truth for every redaction the app performs. It is seeded from the built-in set on first run and falls back to it whenever the file is missing or unreadable, so a broken config can never make redaction *weaker*, and it is authoritative rather than additive — the same contract `copy_redact::redact_for_clipboard` already had. Writes go through `store::write_private_json`, so the file lands at `0600` like the rest of the config directory; the original code used a bare `fs::write`, which measures `0644` under the default umask (latent, since nothing reached those functions), and its `seed` created the parent directory while its `reset` did not. Settings gains a "Redaction rules" section that lists each pattern and its replacement and edits them in place — add, update and delete, plus a confirmed "Restore defaults"; see Changed for the guardrails that replaced an earlier read-only revision. CLI, MCP and daemon exposure is not part of this change. `load_user_rules` is deliberately uncached: it read and recompiled per call before, as `default_rules()` already did on the same path, and an mtime-keyed cache would have to cope with filesystem mtime granularity, where writing a file and reading it back in the same tick is not guaranteed to invalidate.
- **The three configuration lifecycles on the CLI, MCP and daemon**: `redaction.rs`, `highlight.rs` and `ssh_algo.rs` each carry a complete lifecycle — seed, load, add, update, delete, reset — and each was reachable from the desktop Settings panel and from nowhere else. They now reach all three automated surfaces, 13 operations apiece: `agent2ssh redact | highlight | algo`, the MCP tools `ssh_redact_rule_*`, `ssh_highlight_rule_*` and `ssh_algo_prefs_*` (`tools/list` grows from 58 to 71 entries), and the daemon's `GET|POST /redact/rules`, `POST /redact/rules/{update,delete,reset}`, the same four under `/highlight/rules`, and `GET|PUT|DELETE /algo/prefs`. Four decisions shaped the shape of it. First, `--daemon` is a *global* CLI flag, so a subcommand that ignored it would read the local file and print a confident wrong answer for `agent2ssh --daemon prod redact list` — worse than not supporting it — and all 13 commands route through one `remote_config` helper that resolves the alias, attaches the bearer token and decodes the response, rather than 13 near-identical functions each of which could get the auth header wrong. Second, a rule's pattern or keyword *is* its identity, and a regular expression (`(?i)password`) is not usable as a URL path segment, so identity travels in the request body and update and delete get their own POST paths instead of `/{pattern}`; this is the same reason `/approval/policies` is a body-carrying `PUT`. Third, removing a rule is confirmed on every surface — `--force`, `force: true` — because removing a redaction rule stops that class of secret being redacted in every audit record, webhook notification, playbook result and diagnostic export, while removing a highlight rule hides nothing the app writes but is still gated so a mistyped keyword cannot quietly drop a rule the user meant to keep. The check is repeated in all three layers rather than shared, because a client that speaks HTTP to the daemon never passes through the CLI or the MCP handler, and an MCP client that sends `"force": false` satisfies a `required` list that only proves the key is present. Fourth, `algo` is a singleton rather than a list — one `SshAlgoPrefs` of eight comma-delimited algorithm lists — so it is get/set/clear rather than five operations, and `set` starts from what is in effect and overrides only the lists the caller named, so tuning key exchange does not silently reset the other seven. `AlgoPrefsState` — the effective preferences, whether they are an override, and the defaults they fall back to — moves out of `tauri_commands.rs` into `ssh_algo.rs` so all four surfaces serve the same snapshot; it could not stay behind `#[cfg(feature = "tauri")]`, which the CLI, MCP and daemon do not compile with. `--literal` escapes the keyword at the call site rather than by handing `insert_rule` an `is_regex: false` rule, because that field is a migration input: `normalize_rule` consumes it by escaping the keyword and writing `true` back, so no non-regex rule is ever stored and `--literal` on a rule whose keyword is already escaped would escape it a second time and change what it matches. `highlight update --literal` therefore requires `--new-keyword`, and `highlight list` does not print a regex/literal column, because every stored rule is a regex and the column would say the same thing for all of them.
- **CLI contract tests run in CI**: `src-tauri/tests/cli_contract.rs` has covered the CLI's observable surface — argument parsing, exit codes, help text, version output and error messages — since B39, and no CI step ran it. The `build` job's cargo-test steps named `--lib`, `--test daemon_integration`, `--test cli_smoke` and `--test connect_deadline`, and `contract-consistency` ran nine name-filtered cases out of the first two of those suites. So the suite — 30 tests, 29 of them older than this change — could not fail a pull request, and the lifecycle contract test added by the previous change would have joined them as decoration. `build` gains a `Rust CLI contract tests` step alongside the `cli_smoke` one, so the whole suite now runs on all three platforms; it needs no fixture, because every test spawns the real binary against a temporary `AGENT2SSH_CONFIG_DIR`. `exec_fixture` deliberately stays out of the matrix: it needs the containerized sshd that `scripts/e2e-docker.sh` starts, which is why it runs from the `real-ssh-e2e` job and nowhere else.

### Changed
- **The SSH transport is now `russh`, and the default build no longer links OpenSSL**: the connection layer used to be libssh2 through the `ssh2` crate, which on Windows meant building OpenSSL from source to escape WinCNG's MODP-only key exchange — a C toolchain, a full Perl, and a `OPENSSL_SRC_PERL` indirection that existed only to find one. The transport is now `russh` with `ring` as its crypto backend, so the default build's SSH dependency is `russh` alone: `ssh2`, `libssh2-sys` and `openssl-sys` are not compiled, not linked, and there is no `libssl`/`libcrypto` DLL to ship or to be missing on a user's machine. What the swap had to preserve was not the API but the behaviour underneath it: stdout and stderr arrive on one channel and are read as two independent cursors that only report EOF once both are drained, the blocking flag and the timeout stay separate so the exec teardown can switch to blocking and then wait for close, and `wait_close`/`exit_status` keep their ordering. Those are the paths an exec, a PTY session and a health probe all share, and the suite that was written for exactly those failure modes passes against a real sshd. SFTP is wired through `russh-sftp` (1 MiB upload and download byte-identical, and both resume directions complete a half-written file), remote forwarding is adapted from russh's push model back into the pull-based `Listener` the rest of the code expects, and the pre-auth banner is captured again rather than reported as absent. Two things are knowingly not at parity yet and both fail closed rather than degrading: `agent()` authentication (including Windows Pageant) returns `unsupported` until it can be verified on Windows, and the server's advertised authentication methods are no longer available, so a method the server never offered is attempted and refused instead of being skipped. The libssh2 backend itself is deleted in the same release, not kept behind a feature: it never shipped in this form, so there is no installed base to protect, and a rollback path that nobody exercises is a second implementation that rots.
- **Windows is no longer described as the constrained platform**: `ssh_key_format::reads_openssh_private_keys` and `ssh_algo::safe_defaults` derive their answers from a capability probe rather than a platform check, so both flipped on their own with the backend — `agent2ssh keys algorithm` now reports `ed25519` on Windows, the generated key is written as the OpenSSH container rather than RSA PEM, and the negotiated algorithm defaults are the same list Linux and macOS read. What did not flip on its own was the prose, and stale prose about a platform's limits is indistinguishable from a current limit to whoever reads it next: `scripts/e2e-container.sh` told a Windows reader to point the fixture at an OpenSSH 9.x server, `ssh_key_format`'s user-facing diagnostic named "the Windows build" as the WinCNG one, and `AGENTS.md`, the configuration guide, the CLI quickstart and the bundled skill all repeated the same equation of Windows with WinCNG. These now state a property of the *build*: the diagnostic says "this build's libssh2 links the WinCNG backend", which stays correct on a build that has one and stays accurate on one that does not. `docs/guides/configuration-guide.md` merges the two former caveats into the current behaviour, because the second of them — "Windows cannot connect to OpenSSH 10.0 or newer at all" — had become simply false. The E2E harness keeps `AGENT2SSH_E2E_IMAGE` as a genuine escape hatch and its failure message now says what it is for: a WinCNG build needs the 9.x fixture, and every platform this repository builds does not, so an unreachable sshd on such a build is a real failure rather than the expected one.
- **The real-SSH E2E harness provisions its client key through the app**: `scripts/e2e-container.sh` generated its client with `ssh-keygen -t ed25519`, so the suite could pass while the keys the app itself hands a user were unusable — the harness's key and the product's key came from different code paths, and an ed25519 key in the OpenSSH container cannot authenticate on Windows at all. The script now asks `agent2ssh keys algorithm` for the type and runs `agent2ssh keys generate` for the pair, which turns the entire run — readiness, exec, SFTP, and all four `exec_fixture` tests — into a regression test for app-generated keys, and authorizing that key through `PUBLIC_KEY` is what checks the app's public-key encoding against a real sshd rather than against its own parser. Readiness is polled through the app instead of a stock `ssh` client, so the client under test is what judges the fixture to be up; a system `ssh` remains as a deliberate independent cross-check, tolerating the known Windows refusal of a temp-directory key's ACLs rather than counting it as a failure. The script no longer requires `ssh-keygen` at all. It also stopped mangling remote paths on Windows: Git Bash rewrites any POSIX-looking argument into a Windows path before a native binary sees it, which is what makes `--key "$WORK/…"` and `-i "$WORK/…"` work and what turned `/config/payload.bin` into `C:/Program Files/Git/config/payload.bin`, failing every SFTP step against the server with `[SFTP(2)] no such file`. Local and remote paths cannot be told apart by shape, so the container prefix is excluded from the rewrite (`MSYS2_ARG_CONV_EXCL`) instead of the rewrite being disabled globally. `AGENT2SSH_E2E_IMAGE` selects the sshd image, which is what lets a Windows host run the suite against the OpenSSH 9.x server the WinCNG backend needs; the script's failure message now says so, because OpenSSH 10.0 removed the MODP Diffie-Hellman groups that backend offers and the handshake then has no common key-exchange algorithm at all.
- **The real-SSH E2E harness no longer assumes Docker**: `scripts/e2e-docker.sh` began with `command -v docker`, called `docker` at each of its four container operations, and named the runtime in its own filename, so the only regression that exercises the real libssh2 transport ran on Linux CI and on machines that happen to have Docker — not on a Windows host with wslc or a Mac with Apple's container runtime. It is now `scripts/e2e-container.sh` and asks `agent2ssh containers runtime` which runtime to use, so the harness and the app share one selection policy instead of the script carrying a second copy of it. Only the binary path differs between the three: `run -d --name -e -p <image>`, `logs` and `rm -f` are accepted by all of them (`wslc` documents `rm`/`delete` as aliases of `remove`, and Apple's command reference titles its command "delete (rm)"). The old filename survives as a compatibility shim, because reports and downstream scripts reference it; the rename itself is not cosmetic, since a reader who saw `e2e-docker.sh` would reasonably conclude the suite is Docker-only.
- **The settings panel uses the shared button primitives**: `SettingsMenu` was the last file in the app that hand-wrote every button it owned — 23 raw `<button>` elements built from two local class constants, with neither `<Button>` nor `<IconButton>` anywhere in it. It had been queued as a follow-up on the assumption that `Button` had no size for the panel's dense small buttons, and that premise did not survive contact: `IconButton` has carried the small square all along (`sm` is `size-7`), and 20 of the 23 sites are `h-9` full-width rows rather than small buttons. The premise that these were 23 different hand-rolled styles did not survive either — the two constants covered 20 of the sites, and one of them had grown a second shape as `cn(rowBtnCls, "justify-center px-2")` at eight more. What `Button` actually lacked was *shape*, not size: it is `inline-flex` and sized by its label, so it had no way to say "fill the container" (five call sites wrote `className="w-full"` by hand) and none to say "align the content left", which is what separates a settings row from a button. `Button` gains two additive axes, `block` and `align`; `defaultVariants` is untouched, so all 85 existing call sites are unchanged. The 23 sites become 22 `<Button>` and one `<IconButton>` — the close key, whose `X` is 15px, because `Button`'s base carries `[&_svg]:size-4` and `IconButton` deliberately does not resize the glyph it holds. Equivalence was measured rather than assumed: rendering each site's props through the real `cva` and diffing the class tokens against the string it replaced removes zero tokens in six of seven shapes, and the seventh only loses a `px-2.5` that `tailwind-merge` was already collapsing. That diff caught one real regression — `variant="outline"` brings `hover:bg-muted`, and a selected theme swatch had no hover classes before, so the primary tint would have been painted over on pointer-over and the selected theme would have read as unselected; the selected branch now restates its hover pair. Five changes are visible, all of them the price of adopting the shared spec: `cursor-pointer` on all 23 (they showed the default arrow), a `focus-visible` ring, glyphs at 14px instead of 16px — which is what every other `Button` in the app already renders, since `[&_svg]:size-4` is `calc(var(--spacing) * 4)` and this app sets `html { font-size: 14px }` — `px-4` instead of the UA's `1px 6px` on the seven full-width action buttons, and an explicit `text-foreground` where the panel's `text-popover-foreground` used to be inherited (those two tokens differ only in the `dark` and `nord` themes). `ui/button.test.tsx` pins both new axes and `ui/icon-button.test.tsx` pins why the close key is an `IconButton` at all; writing them first is what caught the axes being defined in the `cva` but never forwarded into `buttonVariants()`, which produced no classes and spread `block=""` onto the DOM while `tsc` and all 121 existing tests stayed green.
- **Redaction rules are editable, including deletion**: The first revision of this change shipped the panel read-only and exposed only "Restore defaults", reasoning that a rule set which can only gain rules cannot be a downgrade: restoring the built-in set re-enables a rule but never removes one, whereas deleting a rule stops a whole class of secret being redacted everywhere the app writes. The asymmetry is real, but it was the wrong thing to build the boundary on. The terminal highlight rules are edited in full thirty lines up in the same panel, so this restriction did not make the feature safer than its siblings — it only pushed add, update and delete back to hand-editing `redact_rules.json`, a file nothing in the app pointed at. The panel now offers all four operations, and the guardrail moved from withholding the operation to framing it: deleting opens a confirmation that names the consequence, built-in rules carry a badge so that confirmation can say a whole class of secret is about to stop being redacted, an empty replacement renders as `(removed)` rather than as a blank, and an empty rule set is shown as a warning instead of as a neutral empty list, because an empty `redact_rules.json` is a rule set that redacts nothing. `redaction.rs` gains `list_rules`, `insert_rule`, `update_rule` and `delete_rule` plus two error variants, `Duplicate` and `NotFound`: a pattern is a rule's identity, so a second rule for the same pattern, a rename onto an existing one, or an edit of a pattern that is no longer there are errors rather than silent overwrites, and every mutation validates the regex before writing so a bad pattern cannot leave a half-written set behind. `BUILTIN_RULES` is now one array that both `default_rules()` and the new `is_builtin_pattern()` read, so the seeded set and the marker the UI warns on cannot drift apart. The desktop commands grow from two to five, `RedactRuleInfo` (`pattern`, `replacement`, `is_builtin`) replaces the old wire shape, and the frontend's `RedactRuleConfig` type is deleted — nothing in the frontend reads the file, and after this change the mirror had no reference left.
- **WebDAV sync set convergence**: The desktop and CLI/daemon portable-config file lists were merged into the single `webdav_sync::SYNCABLE_FILES` constant, so every sync path now carries the same files. `webhook.toml` and `app_preferences.json` are synced from every entry point.
- **Local-only configuration files**: `secrets.enc`, `snippets.json`, and `approval_policies.toml` are no longer part of WebDAV sync and do not cross machines. Machines that relied on cloud sync for shared credentials or snippets must migrate them manually.
- **Byte units in the WebDAV Sync panel**: `formatBytes` now reports `KiB`/`MiB` consistently across the UI, replacing the panel's `KB`/`MB` labels.
- **`ExecRequest::timeout_secs` contract**: The deadline bounds how long the client waits, not the lifetime of the remote command. Documented the measured OpenSSH 9.7 behaviour (below) and directed callers that need a guaranteed stop to wrap the command server-side in `timeout(1)`.
- **`exec_multi` reports an empty target list**: `exec_multi_core`, `exec_multi_with_strategy` and `preview_exec_multi` resolve through one `resolve_exec_targets` helper that returns an error (`no hosts matched the requested hosts or tags`) for an empty resolved list, and propagate host/tag resolution failures instead of collapsing them to an empty vector. A `--tags` typo that selected nothing used to look like a successful run: the CLI printed an empty table and exited 0, MCP returned an empty array, the daemon returned 200, and `exec/preview` reported that a command nobody would receive was safe to send. The CLI, MCP server and Tauri command layer now surface it as a failure, and the daemon answers 400 for `/exec-multi` and `/exec/compare` — matching `/exec` and `/exec/preview`, which already used 400 for the same class of error rather than 500.
- **Connection and prompt budgets follow the caller**: `connect_tcp_address` tries every resolved address within one shared budget capped at 30 s, so a host whose unreachable AAAA record precedes a usable A record connects immediately instead of waiting out the first attempt, and a zero-second budget can no longer be passed to `TcpStream::connect_timeout` or `set_read_timeout` (both reject a zero duration). A failed connection now names every address that was tried instead of only the last one, so a host whose A and AAAA records fail for different reasons does not hide the relevant error, and addresses skipped once the budget ran out are reported as such. The keyboard-interactive external prompt wait now follows the caller's SSH timeout instead of a hard-coded 120 s.
- **Shared health-probe client**: `check_health_blocking` reuses one `reqwest::blocking::Client` instead of constructing one per daemon. Each client owns a dedicated runtime thread, so listing N daemons spawned and joined N of them per call.
- **One command-capture implementation**: `BoundedCapture`, the drain loop, `ExecTimeout` and the drain/teardown constants moved from `core` into `embedded_ssh` as `run_command_capture`, which both the exec path and the health collector now call. `core::EmbeddedExecOutput` was field-for-field identical to the new `CapturedExec`, so it is gone.
- **One TCP↔channel bridge**: `bridge_tcp_and_channel` now has a single implementation in `embedded_ssh`. The jump-host `direct-tcpip` bridge and the local/remote port forwarders all call it, with cancellation and the forwarder's live byte counters injected instead of duplicated, so a fix to the read or EOF handling reaches every tunnel rather than one of two copies. The `write_all_tcp`/`write_all_channel` wrappers the second copy needed are private now.
- **Stoppable forward writes**: `write_all_tcp` and `write_all_channel` gained `_with_stop` variants, and the port-forward bridge checks the stop flag between reads and inside each write loop. Removing a forward now interrupts an in-flight write instead of leaving the connection thread blocked until the peer drains, and the remote-forward target connection is opened through `connect_tcp_address` with a 5 s budget rather than an unbounded `TcpStream::connect`.
- **One name for the config-directory override**: `store::CONFIG_DIR_ENV` replaces 98 inline `"AGENT2SSH_CONFIG_DIR"` literals across the library and the four integration-test suites. The variable that points the CLI, daemon, MCP server and desktop at an isolated config directory is now declared once, next to the `store::config_dir()` that reads it, instead of being spelled out at every call site.
- **CI actions moved off the deprecated Node 20 runtime**: `actions/checkout` v4 → v7, `actions/setup-node` v4 → v7, `actions/cache` v4 → v6 and `softprops/action-gh-release` v2 → v3. Every run was emitting a Node 20 deprecation annotation because those releases target a runtime GitHub has started forcing onto Node 24. None of the intervening breaking changes apply here: checkout's fork-PR block only covers `pull_request_target` and `workflow_run` triggers (this workflow uses `push`/`pull_request`/`release`), and the rest are ESM migrations plus a runtime bump. `dtolnay/rust-toolchain` is a composite action with no Node runtime and stays as-is.
- **G13's "one-way import only" conclusion is narrowed**: `docs/rssh-design-analysis.md` recorded that exporting back to the system `known_hosts` was impossible — a trusted-host record keeps only a SHA256 fingerprint and no public key — and concluded the feature would therefore stay import-only. Only the export half is impossible: deletion matches on hostname, never on key material. The entry now says which direction is blocked and which is not, and its status line reads import plus forget rather than "known_hosts 双向导入导出".
- **One session input splitter**: The function that turns a session's pending buffer plus newly written bytes into whole commands plus a trailing fragment existed twice, byte for byte — in `tauri_commands.rs` for the desktop write path and in `bin/agent2ssh-daemon.rs` for the websocket handler. That splitter is what makes a fragmented write safe to authorize: a write can end mid-line, so a caller that authorized only the bytes it just received would let a command be assembled across several writes and run without ever being approved. Both surfaces therefore had to agree on how a line closes, and an edit to one copy that missed the other would have been a quiet authorization hole. It is now `session::split_completed_session_commands`, and the daemon needed no import change because it already glob-imports `agent2ssh::session`.
- **One multi-host authorization loop**: The desktop, CLI and MCP exec paths each carried their own copy of the same thirty-line loop — expand the host/tag selection, authorize each target individually, and collect the high-risk hosts that came back approved so `force` can be flipped for exactly those. That loop is where the multi-host authorization rule lives, so three copies meant three places that had to agree on it. It is now `execution_control::authorize_targets_without_approval_handler`, and each surface keeps only what is genuinely its own: the rejection wording, which is forwarded verbatim, and the rendering of the returned error (`String` for desktop, `anyhow` for the CLI, `McpError` for MCP). The expansion failure used to be mapped per-surface and is now folded into `CommandAuthorizationError::Internal` with its original message; all three surfaces already render `Internal` as the bare message, and `McpError::from(anyhow::Error)` is also `McpError::internal` with code `-32000`, so the text and code a caller sees are unchanged.
- **Shared proxy field trimming**: `core::normalize_proxy` and `store::normalize_config` each carried the same fourteen lines of proxy cleanup. Only the cleanup is common, so only the cleanup moved — `ProxyProfile::trim_fields` is a pure in-place trim. The failure policy deliberately stays per-surface: `normalize_proxy` validates a single proxy the user just submitted and names the first missing field, because that string goes back to the user, while `normalize_config` repairs a loaded `hosts.json` and silently drops entries that fail the same required-field checks, because one bad entry should not cost the whole file.
- **Audit-entry tests build on a fixture**: Fifteen test literals spelled out all thirteen fields of `AuditEntry`, mostly just to say "fresh id, fresh timestamp, every optional field empty". Each of the last four fields the struct gained — `side_effect`, `source`, `action`, `outcome` — had to be added to every one of them. They now override only what they assert on and take the rest from `AuditEntry::test_fixture()`. Sites that need a specific timestamp still pass one (anomaly offsets from now; the 5000-entry store test derives from a fixed epoch), because an explicit field beats the struct-update spread.
- **A test config directory that cleans up after itself**: Six modules each rebuilt the same scratch config directory — `temp_dir().join(..)`, `create_dir_all`, `store::set_test_config_dir`, and a cleanup call at the end of the test that every early `assert!` skipped. `store::TestConfigDir` now does all three in one guard and removes the directory when it drops. Two of the six were also wrong: `highlight`'s teardown only cleared the thread-local override and leaked the directory on every run, and the three `forward.rs` tests derived their path from `std::process::id()`, so tests in the same process shared one directory instead of getting their own.

"animate-spin" : ""}`, while eleven different sites swapped the button's glyph for `Spinner`. Only one of those two answers went through a component — with an `aria-hidden`, a default size and tests — and the other was re-decided across seven distinct busy expressions in six files (`refreshBusy`, `healthBusy`, `updateBusy === "check"`, `daemonActionBusy === "restart"`, `diagnosticBusy === "refresh"`, and more). All eleven now swap in `Spinner`. This direction was chosen over adding a `BusyIcon` because it needs no new abstraction and leaves one thing that turns instead of two named ones; the cost is that a button's glyph becomes a loading mark while its action is in flight, which is also the one visible change. `SettingsMenu` keeps its own 16px marks and `RecordingsPanel` keeps its inline label, since neither was part of the duplication. Two `IconButton` refresh marks move 14 → 15 to match the five static ones beside them — both sizes genuinely rendered, so a click used to shrink the glyph by a pixel as it started turning. Four `size` props are dropped rather than migrated: the shared `Button` base carries `[&_svg]:size-4`, which targets the `svg` element itself and so outranks the SVG `width` presentation attribute, meaning `size` inside a `Button` never applied and removing it changes nothing. The `progress` toast variant is folded in as well, since it spelled "spin" by hand a third time; it has no call sites today and its rendered class set is identical, so only the claim in `Spinner`'s own doc comment changed — it is true now.
- **One host picker**: `HostSelector` existed and three panels used it, but four more hand-rolled the same single-select over the `hosts` array, and they had drifted in four ways at once — three option texts (`name`, `name (host)`, `name - user@host:port`), two framings (bare in a toolbar, plain text under a heading), and a disagreement about the one thing that matters: whether an empty value is an answer. That is not a style difference. `ForwardPanel`'s jump host and `AddHostForm`'s bastion are optional, so `""` has to survive as a real answer, while the settings panels must never leave a stale host name in the field and so force a real host. `HostSelector` already knew how to force one; it had no way to express "none is fine", which is the whole reason the other four sites could not use it. The distinction is now a prop — `allowEmpty` says `""` is legal, so the control stops auto-selecting and stays usable with an empty host list — and `emptyOption` separates a blank entry the user may choose (`None`, `Direct connection`) from the placeholder shown when there is nothing to choose at all, which is not an answer. `optionLabel` lets each caller keep its own wording, which is what makes this a zero-visible-change merge, and `shell` plus `selectClassName` cover the two framings. Three sites that look the same are deliberately not: `AddHostForm`'s proxy select reads `proxies` rather than `HostProfile`, `MultiExecPanel`'s host control is a multi-select chip group, and `HostDiffView`'s picker selects a run result rather than a configuration. One deliberate difference remains: when the host list is emptied, a value that no longer names anything is cleared instead of left dangling — the two toolbar sites used to keep it and lean on the submit button's `disabled`, and clearing matches what this component already did for its three existing callers. All five call sites had no test coverage at all; there are now fifteen, asserting what `onChange` receives, whether the select is disabled, and each option's value and text rather than incidental spacing.

- **The embedded skill documents the configuration lifecycles**: `skills/agent2ssh/SKILL.md` is the convention sheet an agent reads before calling any of this, and it described `force: true` for high-risk commands but said nothing about the three lifecycles that live under `~/.agent2ssh/`. The version moves `0.2.1` → `0.3.0` so an existing installation is offered the update; `integrate.rs` compares the installed and embedded versions for equality, so a content change without a version bump would never be installed.

- **The SSH transport moved from `russh` 0.60.3 to 0.64.1**: the upgrade is what makes RSA user certificates usable. 0.60 built the certificate's public-key algorithm name from the certificate's embedded key (`ssh-rsa` → `ssh-rsa-cert-v01@openssh.com`) with no way to override it, so OpenSSH 8.8+ refused every RSA certificate before the signature was even checked; 0.64's `client_make_to_sign` takes the hash and produces `rsa-sha2-512-cert-v01@openssh.com`. Two API changes came with it and are the only code touched by the bump: `check_server_key` now receives a `PublicKeyOrCertificate` (host certificates are unwrapped to the key they vouch for) and `server_channel_open_forwarded_tcpip` gained a `ChannelOpenHandle` that must be accepted explicitly — dropping it sends an administrative rejection. The RustCrypto pre-release pins this repository carried for 0.60 were narrowed to what 0.64 declares: `ed25519-dalek` moved from `=3.0.0-pre.6` to the finished `3`, `pkcs5` from `=0.8.0-rc.13` to the `0.8` line, and `pkcs1` stays pinned because that is still what the transport declares.

### Removed
- **libssh2, OpenSSL and the key-format detector**: the `ssh2` dependency is gone, and with it `libssh2-sys`, `openssl-sys`, the Windows `openssl-on-win32`/`vendored-openssl` block, the `OPENSSL_SRC_PERL` pin in `src-tauri/.cargo/config.toml`, `scripts/win-perl.cmd`, and the CI steps that installed NASM and a Perl for the Windows legs. `ssh_key_format` went too — it existed to explain failures where the crypto backend could not parse a key's encoding, which cannot happen with a single transport that reads every format; `keys algorithm` still reports `reads_openssh_private_keys`, now constant `true`, because that field is part of the CLI's JSON contract. Both the module and the `ErrorKind::Opaque` variant it depended on are deleted rather than left unused.

- **Intel macOS support**: `x86_64-apple-darwin` is no longer built, tested or published. The `build` and `tauri-bundle` matrices drop that leg, so releases no longer carry `agent2ssh-*-x86_64-apple-darwin.tar.gz` and no DMG is produced for Intel Macs. The Homebrew formula's Intel branch now fails with an explicit message rather than fetching an archive that no longer exists, and the README plus the MCP distribution and branch-protection guides list the supported platforms as macOS (Apple Silicon), Linux x86_64 and Windows x86_64. Intel Macs can still build from source; that architecture is simply no longer tested.
- **Four helpers that only forwarded or duplicated a live path**: `AppState::emit_bus`, `Host::is_headless`, `Host::is_cli` and `policy::policy_risk_rules` had no caller anywhere in the repository. `emit_bus` only forwarded to `events::publish_event`, which has 15+ direct callers, so routing emissions through `AppState` would have added a layer without changing behaviour. `is_headless` / `is_cli` restated `transport_name()`, which is the accessor actually used by `diagnostics` and by the audit `source` default. `policy_risk_rules` was the interesting one — it is not an unwired feature but a *worse* copy of `risk_config::load_risk_rules()`: it reads only `policy.toml`'s `risk` table and ignores the standalone `risk_rules.toml` fallback and the mtime cache `load_risk_rules()` provides, so wiring it up would have silently dropped every rule that file declares. All four are gone, along with the `TODO(unwired)` notes that had outlived them. `Host::emit` is **kept**: it is covered by tests and is the migration target the `Host` enum documents for `app.emit()`.
- **The test-only glob matcher in `ssh_config.rs`**: Include expansion goes through the `glob` crate — `splice_pattern` checks `has_glob_meta` and hands the pattern to `glob::glob` — but the module also carried a hand-rolled `glob_match` / `glob_match_bytes` / `char_class_match` (about 95 lines, all `#[cfg(test)]`) that no production path called. It existed only so six unit tests could exercise it, which meant those six were testing a copy of glob's semantics rather than anything this crate does. `include_splices_glob_matches` and `include_splices_multi_level_glob_matches` build real `config.d` trees in a temp dir and assert on what `load_with_includes` returns, so include expansion itself stays covered. `has_glob_meta` is production code and keeps its test.
- **The `rand` dependency**: `backup_crypto` was the only place in the crate that pulled in `rand`, and only for two `thread_rng().fill_bytes()` calls filling the Argon2 salt and the AES-GCM nonce. Every other entropy call site — `keys.rs`, `mcp_binding.rs`, `secrets.rs` — already used `getrandom::fill`, so dropping it leaves one RNG entry point instead of two that had to stay consistent. No behavioural change: `thread_rng` is itself seeded from the OS CSPRNG. `cargo tree -i rand` showed `agent2ssh-app` as the sole reverse dependency; `rand_core` / `rand_chacha` / `ppv-lite86` stay in the lock because other transitive crates still need them.


### Fixed
- **Final regression review**: agent connection and identity-list timeouts discard only the agent stream so SSH key fallback still works; SFTP subsystem setup now waits for success/failure before initializing the protocol; desktop uploads use the same encrypted-size limit as downloads and fail before contacting WebDAV when oversized.
- **Desktop WebDAV uploads are encrypted and exclude local secrets and runtime files**: the desktop now collects only `SYNCABLE_FILES`, excluding private SSH keys, the credential vault, host-key trust and active forwards. A separate sync password is stored in the encrypted credential vault after the master password is set or unlocked; it is write-only in the UI. Uploads fail before contacting WebDAV when that password is missing or unavailable, including old enabled configurations. The desktop encrypts its JSON snapshot as one AES-256-GCM blob with an Argon2id-derived key; this single-file format is separate from CLI/daemon versioned sync. The desktop now also downloads encrypted backups and restores them after validation, with a local undo snapshot and rollback on write failure. After downloading the ciphertext from WebDAV yourself, `agent2ssh webdav decrypt <input> <output> [--sync-password-env VAR]` recovers the original JSON snapshot offline using the saved independent sync password, read from `AGENT2SSH_SYNC_PASSWORD` by default. It refuses to overwrite existing files and does not connect to WebDAV or apply the snapshot to the current configuration.
- **Config snapshot restore now removes files that did not exist in the snapshot**: restoring the pre-template snapshot undoes newly created policy and execution-limit files, and restores the presence or absence of `sync_version.json`. The complete manifest and captured files are checked before any live configuration change, a pre-restore safety backup is retained, and non-syncable credentials and local trust are left intact.
- **Desktop recursive SFTP deletion reaches the daemon approval flow without losing unlocked credentials**: confirming a directory deletion submits `/sftp/rm-rf/authorize` for the shared scope, gate, limits, risk and approval checks. The daemon only authorizes; the desktop verifies the returned host/path and performs the deletion in its own process using its already unlocked credential vault. Credentials do not cross processes, and there is no force or approval-bypassing fallback. Blocked roots remain blocked. The existing `/sftp/rm-rf` still authorizes and executes in the daemon and accepts optional `timeout_secs` for SSH/SFTP transport operations.
- **SSH authentication and channel setup honor the session timeout**: password, key and agent authentication, agent identity/signature requests and channel setup now end when their transport deadline expires. A server rejection of an exec, shell, PTY or subsystem request returns the rejection immediately instead of appearing as successful setup followed by a stall.
- **Closing a busy resident session cancels its work**: close can reach an executing session, cancel active and queued commands, and reclaim the shell's process tree. Session metadata and buffered-output reads remain available while a command is running instead of waiting for its timeout.
- **Resident-session access now respects scoped tokens**: lists filter by the session's host/tags, buffered-output reads authorize `resident-session read`, and closing authorizes `resident-session close` through the shared gate, limits, risk and approval checks. Real-daemon regressions cover denied and allowed scopes, command deny precedence, paused execution and approval rejection/acceptance.
- **SFTP file operations preserve exact filenames and root paths**: the desktop consumes structured directory entries instead of parsing display-oriented `ls` text, preserving repeated/edge whitespace, arrows, newlines and literal backslashes. Joining a child under `/` stays absolute on both remote and local POSIX paths. Cancelled batches report actual completed files and retain the source selection; parallel workers settle before the UI releases the batch.
- **SSH channels terminate when the peer closes without EOF**: closing or losing the channel reader ends both input streams after their buffered data drains, preventing terminal polling loops and false exec timeouts. Blocking reads also recheck queued data before sleeping to avoid missed notifications.
- **MCP local execution no longer abandons daemon requests after 30 seconds**: `local_exec` and resident-session tools retain a bounded connect timeout while leaving command, shell-warmup and approval deadlines to the daemon. Regressions drive the real MCP binary through responses delayed beyond 30 seconds.
- **SSH-agent certificate identities remain certificates throughout authentication**: the transport offers the complete certificate and asks the agent to sign using its certificate blob instead of silently converting it to a bare public key. An in-memory CA-only SSH server rejects the bare key and accepts the certificate in the regression test.
- **An encrypted ECDSA key in the traditional PEM container could not be loaded**: `ssh-keygen -m PEM -N <pass>` writes the EC key as SEC1 under `-----BEGIN EC PRIVATE KEY-----` with OpenSSL's `Proc-Type: 4,ENCRYPTED` / `DEK-Info:` headers. The transport decrypts that container itself, but then parses whatever it decrypted as PKCS#1 — so an EC key failed with `Pkcs1: PKCS#1 ASN.1 error: expected INTEGER, got OCTET STRING`, while the same key unencrypted loaded fine and an encrypted *RSA* key in the same container also loaded fine. `legacy_pem` now decrypts the container before the loader sees it (AES-128/192/256-CBC with the MD5 `EVP_BytesToKey` derivation the format specifies) and hands back a plaintext PEM, which `decode_secret_key` already parses for every key type — no temporary file, no second key parser. A wrong passphrase now says the padding did not validate instead of reporting an ASN.1 error. The matrix's `ecdsa256-pem key, encrypted` case moved from a recorded limitation to a pass.
- **RSA user certificates were signed with the legacy `ssh-rsa-cert-v01` type, so OpenSSH 8.8+ refused them**: the certificate path went through `authenticate_openssh_cert`, which signs with `signature::Signer::try_sign` — SHA-1 for an RSA key — and takes no hash to override it. Certificates now go through `authenticate_certificate_with` with a `LocalKeySigner`: a private key used as a `Signer`, choosing the hash the caller asks for and writing the signature in the wire form the packet expects (`string(string algorithm || string signature)`). RSA certificates get SHA-2 even when the server advertises nothing, because SHA-1 is never valid for a certificate on a current server. Verified against OpenSSH 8.3 through 10.3 in the matrix, with the server log showing `Accepted publickey ... RSA-CERT ... CA ED25519` — including a CA-signed RSA key that authenticates with no entry in `authorized_keys`.
- **RSA keys were offered with the SHA-1 `ssh-rsa` signature, so every server from OpenSSH 8.8 rejected them**: `best_supported_rsa_hash` returns `Option<Option<HashAlg>>`, and flattening the two levels turns *the server said nothing* into *use SHA-1* — which `PrivateKeyWithHashAlg::new(key, None)` does literally. Against OpenSSH 10.3 the server log read `userauth_pubkey: signature algorithm ssh-rsa not in PubkeyAcceptedAlgorithms`, while the same key authenticated fine with `ssh`. The unknown case now resolves to SHA-2 and falls back to SHA-1 only after the modern signature is refused, which is the order russh's own documentation recommends and what a pre-7.2 server needs. Found by `scripts/e2e-ssh-matrix.sh`, which reported all six servers rejecting every RSA key including 3072-bit and PEM.
- **User certificates were silently not presented**: `userauth_pubkey_file` took the `-cert.pub` sibling in a parameter named `_pubkey` and dropped it, so a `TrustedUserCAKeys` server saw the bare key — not in `authorized_keys` — and answered `the server rejected these credentials`. The certificate is now read and presented through `authenticate_openssh_cert`, which the matrix confirms with `Accepted publickey ... ED25519-CERT ... CA ED25519` for ed25519 and ECDSA. RSA certificates remain unsupported by the transport; see KNOWN-ISSUES K10.
- **SSH agent authentication failed on Windows whenever Pageant was not installed**: the agent probe tried Pageant first, and `pageant::PageantStream::new()` reports success even with no Pageant running — its WM_COPYDATA transport is created before anything can tell — so the first real request died with `early eof` and the OpenSSH named pipe was never reached. The pipe is now tried first, since opening it fails immediately when nothing listens, and Pageant is the fallback. Verified against the Win32-OpenSSH agent service with two identities loaded and only the second authorized, plus a negative control that clears the agent and watches the same command fail.
- **A silent peer left the connect worker parked forever, holding a thread and its socket**: the deadline the facade receives from `set_timeout` bounded channel I/O but not the handshake, so a peer that accepts TCP and then sends nothing kept the connect awaiting a banner with no end. `ping_hosts_core` and `collect_health_snapshot` wrap a connect in `tokio::time::timeout` and returned on schedule, which hid the leak: the abandoned `spawn_blocking` worker stayed blocked on the future, holding one thread and one socket per host, per poll. The handshake now takes the same deadline as the rest of the session and drops the stream when it expires, which is what releases the worker. `tests/connect_deadline.rs` asserts it from the peer's side — the silent listener must observe EOF — and both of its cases pass again; they failed on the russh transport, on all three CI legs.
- **SFTP uploads to Dropbear failed or stalled**: a write over 32 KiB came back from libssh2 as zero bytes ("failed to write whole buffer"), and a stream of 30000-byte writes stopped for good after 128 KiB, leaving the remote file at 131072 bytes (measured against Dropbear 2024.85; 1 MiB uploads hung, downloads were fine). Uploads now use 16 KiB writes when the server banner says Dropbear, which completes a 1 MiB upload; every other server keeps 64 KiB writes, which are about 2.6x faster than 16 KiB against OpenSSH (28 vs 11 MB/s over loopback), so the fix is not applied globally. A write that still reports zero bytes now halves its size and retries instead of failing. Found by the connection matrix's SFTP case.
- **RSA keys could not authenticate to servers that accept only SHA-1 `ssh-rsa` signatures** (OpenSSH before 7.2, many embedded devices): libssh2 offers `rsa-sha2-*`, the server refuses, and the key looked unauthorized (`Username/PublicKey combination invalid`). After the modern signatures are refused, public-key authentication is retried once with `ssh-rsa`. That is the signature the server insists on, not a downgrade the client invents, and the host-key list already ends in `ssh-rsa`.
- **A key-exchange failure said only "Unable to exchange encryption keys"**: the built-in algorithm defaults are modern on purpose, so a server offering only SHA-1 key exchange, CBC ciphers or SHA-1 MACs fails there with libssh2's bare `-5`. The error now says that no algorithm is common to both sides and points at `agent2ssh algo get` / `algo set`, which is what makes such a server work (verified against OpenSSH 8.3 restricted to `diffie-hellman-group14-sha1`, `aes128-cbc`, `hmac-sha1` and `ssh-rsa`).
- **Integration tests rewrote the developer's real `~/.agent2ssh`**: `cli_contract`, `cli_smoke` and `daemon_integration` spawn the CLI/MCP binaries or call core functions in-process (approvals, hosts, webhooks) without setting `AGENT2SSH_CONFIG_DIR`, so a plain `cargo test` read and wrote the real config directory; one such run emptied a real `approvals.jsonl`. `src-tauri/tests/common/mod.rs` now points every integration-test process at a fresh temp directory (and the in-memory secrets backend) from a constructor that runs before `main`, panics if `AGENT2SSH_CONFIG_DIR` already names the real directory, and `exec_fixture`/`connect_deadline` restore that default instead of removing the variable. Verified by running all five integration binaries with the variable unset and comparing checksums of the real directory before and after.
- **Risk classifier no longer misses equivalent spellings of destructive commands**: `classify_risk` relied on `lower.contains(...)` substring rules, so `rm --recursive --force /`, `rm -rf / --no-preserve-root`, `dd of="/dev/sda"`, `systemctl  stop sshd` (two spaces), `iptables --flush`, `DROP  TABLE`, `chmod 0777`, `find / -delete`, `bash -c "rm -rf /var"`, `eval`, `curl … | sh` and `echo … | base64 -d | sh` all classified Low or Medium. A new token-level pass, `src-tauri/src/risk_extra.rs`, parses shell words (quotes removed, long and short options normalised) and unwraps `sh -c`, `eval` and `find -exec` before classifying the inner command again; a pipeline into a shell interpreter is High; block-device writers (`dd`, `shred`, `wipefs`, `tee`, `cp`, …) are Blocked; a command whose program name is a `$var` or `$(…)` expansion is High. It only escalates, so nothing previously Blocked or High can weaken. **Visible change**: a command whose program name is a shell expansion (`"$EDITOR" file`, `$HOME/bin/tool`) and inline interpreter code (`python -c`, `perl -e`, Medium, or High when it calls a delete or process API) now need the same approval as other commands of that tier.
- **Daemon accepted `?token=` on every route and answered every origin**: the query-string token is only needed by the browser WebSocket handshakes, yet any authenticated route honoured it, which puts the token in proxy logs, history and referrers. It is now accepted on `/terminal` and `/exec/stream` only; elsewhere it is ignored and the request is rejected. CORS no longer uses `allow_origin(Any)`: only the Tauri webview origins and loopback hosts (`localhost`, `127.0.0.1`) are answered. Bearer auth was already required, so this narrows exposure rather than closing an open door.
- **"Open in Terminal" for container targets could silently do nothing on macOS**: `launch` spawned `open -a Terminal <script>` detached and deleted the 0700 `.command` launcher immediately afterwards, on the assumption that "Terminal has been handed the path". It had not been: `open` is a short-lived helper that resolves the document path asynchronously after spawn, and the file was already gone by the time it did — Terminal was asked to open a path that no longer existed and the window never appeared, while the fire-and-forget spawn still reported success. Reproduced on macOS 27 against a live Docker probe: two consecutive launches left no `docker exec` process and Terminal.app not even running, while handing the same shape of `.command` file to `open` by hand opened a window fine, which isolated the race to the delete-after-spawn ordering rather than to the OS or the argv. The macOS branch now waits for `open` to exit — surfacing a non-zero status instead of assuming success — and keeps the script alive for a 10-second grace period after a successful launch, because the Terminal-side read of the file is asynchronous; a failed `open` removes the script immediately. The Windows and Linux branches are untouched: there the spawned process *is* the long-lived emulator, so detached spawn remains correct, and `spawn_detached` is now compiled only for the platforms that use it.
- **A private key the server would accept could still be unusable, and the failure said only "unknown error"**: `userauth_pubkey_file` failing on Windows with `[Session(-1)] unknown error` named neither the file nor the reason, so the one actionable fact — that the key's *encoding* is not one this build can read — was invisible. libssh2's private-key file support is per-backend and selected at build time: the WinCNG backend's loader (`_libssh2_wincng_load_private`) tries exactly two PEM headers, `-----BEGIN RSA PRIVATE KEY-----` and `-----BEGIN DSA PRIVATE KEY-----`, and `_libssh2_wincng_pub_priv_keyfile` returns a bare `-1` when neither matches, without calling `_libssh2_error()`. The parser for the OpenSSH container format (`_libssh2_openssh_pem_parse`) is only ever called from `openssl.c` and `mbedtls.c`. That container is what `ssh-keygen` has written **by default since OpenSSH 7.8, `-t rsa` included**, so the default key on a modern machine is the one format the Windows build cannot read. `-1` is not a `LIBSSH2_ERROR_*` constant, so `ssh2`'s `from_errno` has no arm for it and falls through to the generic wording — the message could not have said anything useful even in principle. Measured against a real sshd (OpenSSH 9.9 via wslc, an isolated `AGENT2SSH_CONFIG_DIR` per run, `authorized_keys` verified to hold all three keys): the same RSA-3072 key material exported as PEM authenticated and returned `ok-42` with `Accepted publickey for tester ... ssh2: RSA SHA256:xqAgsGx…` in the server log, while both its OpenSSH-container twin and an Ed25519 key returned `[Session(-1)] unknown error` **with no sshd log line at all** — no authentication request was ever sent, which is what separates a client-side parse failure from a key the server rejected (`-18` is raised when the server answers the pubkey *query*, so a refusal would have been logged). A new `ssh_key_format` module now diagnoses it: `detect_private_key_format` identifies the encoding from the armour header, `reads_openssh_private_keys` asks the build (the client host-key algorithm list stands in for the parser, because the backends that lack the parser are exactly the ones with no Ed25519/ECDSA primitives — so enabling `ssh2`'s `openssl-on-win32` flips it to `true` on its own, with no `cfg!(windows)` anywhere), and `unusable_key_hint` reports only when all three conditions hold: container format, a build that cannot read it, and a failure libssh2 could not describe. The third condition is what keeps the hint from displacing a message that already explains itself, such as `-18` or a wrong passphrase. `authenticate` records the key's detected format in `app.log` before every attempt and returns the diagnosis — naming the conversion, `ssh-keygen -p -m PEM -f <path>` for RSA or DSA keys — in place of the bare error. This also documents a consequence that had no way to surface: `keys::generate_key_core` writes Ed25519 *in that same container*, so on Windows every key the app generates is unusable twice over — unreadable format and no Ed25519 primitive in the backend at all. Whether the app should generate RSA-in-PEM instead is left open; it needs a new dependency, since `ssh-key` emits no traditional PEM. It is no longer open: generation now picks a type this build can read — see Added, "Key generation that produces a key this build can actually authenticate with". This is the *authentication* layer only: the separate key-exchange limitation (WinCNG offers only `diffie-hellman-group*`, which OpenSSH 10.0+ no longer advertises) is unaffected and still blocks those servers before authentication begins. Library tests 649 → 660.
- **The built-in SSH algorithm defaults asked for algorithms the Windows build cannot negotiate, so every connection failed before the handshake**: `safe_defaults()` listed curve25519 for key exchange, ed25519 for host keys and AES-GCM among the preferred ciphers, while `apply_algo_prefs` is deliberately fail-closed — one name libssh2 does not know returns an error instead of dropping the entry — and it runs immediately before every handshake (`embedded_ssh.rs:266`, `:1418`). Which names libssh2 knows is not portable, because `libssh2-sys` picks a crypto backend at build time: with `ssh2 = "0.9"` and no `openssl-on-win32` feature, Windows links libssh2 1.11.1 against WinCNG. Measured on this machine by querying `supported_algs` for all eight method types: key exchange is `diffie-hellman-group-exchange-sha1`, `-sha256`, `group1-sha1`, `group14-sha1`, `group14-sha256`, `group16-sha512`, `group18-sha512` — no curve25519 and no ECDH at all; host keys are `rsa-sha2-256`, `rsa-sha2-512`, `ssh-rsa` and their `-cert-v01` forms — no `ssh-ed25519` and no `ecdsa-sha2-nistp256`; ciphers are the CBC and CTR families plus `3des-cbc`, `arcfour` and `chacha20-poly1305@openssh.com`, with `aes256-gcm@openssh.com` absent. Three of the eight default fields therefore named something the build could not do, and the first one checked, `curve25519-sha256`, aborted the connection before any negotiation. Introduced with A22 (`104b4cc`, 2026-08-12), and invisible since: the last authenticated connection in this machine's `app.log` is 2026-06-21, and the only regression that reaches a real handshake — `scripts/e2e-container.sh` — runs in CI on `ubuntu-latest`, where libssh2 links OpenSSL and every one of those names exists. The same mismatch had already been hit once for compression (`f80e7c5`, "Use only 'none' compression default") and was worked around by hard-coding rather than by asking the build what it supports. The defaults are now a wish list (`desired_defaults`) narrowed per field against `supported_algorithms`, preserving order and never adding an entry; a field whose entries are all unavailable becomes an empty string, which means "libssh2's own list" rather than an equally fatal empty preference. The probe relies on `Session::new()` not connecting and caches one query per method type in a `OnceLock`, so nothing is added to the per-connection path. `safe_defaults_are_negotiable_by_this_build` asserts the invariant rather than the literal strings — every default entry must appear in `supported_algs` for its method type, and `apply_algo_prefs` must accept the result — so it fails on any build whose backend cannot do what the list asks; it is what the Windows leg of the `build` matrix would have caught. Side finding, same shape: the rejection message listed `. _ - @` for a check that also accepted `+`, so both now read one `ALGORITHM_NAME_PUNCTUATION` constant and `rejection_message_lists_every_allowed_character` pins the message to the check in both directions. The bundled skill gains the matching warning — that `algo set` accepts a name this build cannot negotiate and that the defaults read back on Windows are the narrowed ones — under its `Local Configuration` list, and its version moves `0.3.0` → `0.3.1` so an existing installation is offered the update.
- **Redaction-rule failures were all reported as an invalid regex**: `RedactRuleError` carried only `InvalidRegex` and `ZeroWidth`, so the rules-file lifecycle had no way to say "the config directory is unavailable" or "this file is not JSON" and said `invalid regex pattern: cannot determine config directory` instead. It gains `IoError` and `ParseError`, a JSON parse failure is no longer labelled a regex failure, and the message Settings shows names what actually went wrong. Latent rather than live, since nothing could reach those functions before this release.
- **The desktop app reported itself as the CLI**: `Host::is_desktop()` is `matches!(self, Host::Tauri(..))` — it tests the *value*, not whether the `tauri` feature was compiled — but `run_tauri`'s startup comment claimed the opposite ("`is_desktop()` returns true under `#[cfg(feature = "tauri")]`") and the desktop therefore never installed a `Host`. `set_host` had exactly one caller in the whole repository: the daemon's `Host::Headless`. The desktop left the global at its `Host::Cli` default, so the `diagnostics` report showed `"transport": "cli"` and `"is_desktop": false` inside the desktop app, and every transport-aware branch would have taken the CLI path. `run_tauri` now calls `set_host(Host::Tauri(app.handle().clone()))` from its setup hook, the comment describes the real mechanism, and two unit tests pin the value-based semantics so a missed `set_host` cannot pass unnoticed again.
- **CI could not start after that action bump**: This repository restricts Actions to an explicit allow-list whose patterns are matched against `owner/repo@ref` — so they pin the version too — and `softprops/action-gh-release@v2` does not permit `@v3`. Job creation failed and the run reported `startup_failure` with zero jobs, no log and no re-run option. `github_owned_allowed` covers `actions/*` at any version, which is why only the third-party action was blocked. The allow-list now mirrors the versions the workflow pins, the constraint is documented in the workflow header, and `workflow_dispatch` was added so a run that dies during startup can be retried without a commit.
- **stdout/stderr drain deadlock**: `exec_ssh_embedded` drained stdout to EOF before reading stderr. The SSH channel window is shared between the two streams, so a command that filled stderr while still holding stdout open blocked its own writes and the read never returned. Both streams are now read on every pass, EOF is taken from `Channel::eof`, and the deadline is enforced inside the loop. `max_output_bytes` is applied per stream via a head-and-tail accumulator, so a stderr flood can no longer grow the process without bound.
- **Timed-out execs no longer leak a blocking worker**: The timeout path closed the channel while the session had already been switched back to blocking mode, and a blocking `close` waits for a server acknowledgement that only arrives once the remote command exits — so a 2 s deadline on an 8 s command returned after 8 s, and the abandoned `spawn_blocking` task kept the caller's runtime alive. The session now stays non-blocking through the teardown, and the post-drain exchange is bounded by an explicit session timeout instead of blocking indefinitely.
- **Timed-out execs are audited**: A timeout previously returned straight out of the exec and wrote no audit entry, even though the command did run. Timeouts are now recorded with no exit code and a reason of `command timed out after Ns`.
- **Bounded stderr capture**: `max_output_bytes` now caps stderr as well as stdout (each stream keeps its head and tail, and `dropped_bytes` reports the total discarded). Stderr was previously read to EOF with no limit, so a chatty remote command could grow the process without bound.
- **WebDAV failures are surfaced**: The desktop sync actions and the automatic post-change sync now read `lastSuccess` off the returned status. Failures previously showed a success toast, and automatic sync failures produced no toast and no diagnostic at all, because the backend reports sync errors as a status rather than as a rejected call.
- **Unix PATH detection**: `path_contains_dir` splits on the platform separator (`:` on Unix, `;` on Windows) instead of always `;`. Splitting on `;` made the whole Unix PATH a single segment, so the CLI status panel always reported the binaries as absent from `PATH`.
- **Ephemeral-port port forwards**: `bind_port = 0` now binds IPv6 loopback on the port IPv4 actually received. Binding both stacks on the literal `0` gave them two different ephemeral ports while only IPv4's was recorded, so clients resolving `localhost` to `::1` reached the wrong port.
- **The confirmation dialog's Cancel button was never translated**: `ConfirmDialog` defaulted `cancelLabel` and `confirmLabel` to the string literals `"Cancel"` and `"Confirm"` instead of running them through `t()`, and six of the seven `confirmDialog()` callers omitted `cancelLabel` — so each of those six rendered an English Cancel button in the Chinese UI, while `"Cancel"` sat translated in the zh map for the fourteen other call sites that spell it out. The defaults now resolve through `t()`, which makes the omission unreachable for future callers as well, and `"Confirm"` gained the zh entry it had never needed until the default could actually render.
- **`highlight_rules.json` was readable by any local account**: `highlight::save_rules` wrote the rule file and stopped there, so on Unix it landed at whatever the umask allowed — `0644` (`-rw-r--r--`) under the usual `022` — while about forty call sites across sixteen files hold every other file under `~/.agent2ssh/` at `0600`. `copy_redact_rules.json` did harden itself, and its comment records that an earlier module-local helper was Unix-only and silently did nothing on Windows; `highlight` never had the step on either platform. Both writers now go through `store::write_private_json`, which cannot be bypassed by a caller that forgets, and `highlight`'s regression test pins the `0600` mode.

### Added

- **Build defaults**: Local Tauri bundles no longer create updater signing artifacts by default, so builds do not require `TAURI_SIGNING_PRIVATE_KEY` unless release signing is explicitly enabled.

### Added
- **Control-plane safety layer**: Added daemon-level execution gate controls, execution rate/session limits, unified policy-as-code validation, and audit-window anomaly detection.
- **Execution gate**: Added `agent2ssh pause/resume/status`, daemon 423 rejection for paused non-desktop sources, gate audit entries, and `gate_rejected` / `gate_changed` events.
- **Execution limits**: Added `execution_limits.toml` with per-source, per-host, and per-tag rate/session limits, plus 429 rejection auditing and `limit_rejected` events.
- **Unified policy files**: Added `policy.toml` / `policy.json` support for colocating risk rules and approval policies, with `agent2ssh policy validate` and `agent2ssh policy test`.
- **Anomaly detection**: Added `anomaly.toml`, source burst detection, sensitive command pattern detection, after-hours high-risk detection, `anomaly_detected` events, webhook support, and Live Activity anomaly highlighting.
- **Embedded jump-host and forwarding transport**: Added embedded `direct-tcpip` bastion proxy channels plus local/remote forwarding over the in-process SSH transport, removing the remaining system `ssh`/`scp`/`sshpass` runtime dependency from exec, SFTP, terminal, session, connection, health, and forward paths.
- **Terminal limit coverage**: WebSocket `/terminal` now participates in daemon session concurrency limits and applies execution rate limits to completed terminal input lines.
- **Embedded SSH key generation**: Local Ed25519 key generation now uses the Rust backend and the operating system CSPRNG instead of shelling out to `ssh-keygen`.
- **Portable daemon lifecycle control**: Daemon status/stop/restart and health checks now use Rust process and HTTP APIs instead of shelling out to `kill`, `taskkill`, `tasklist`, or `curl`.

### Changed
- **Approval scoping**: Multi-host execution and playbook approvals now apply only to the approved host or step. Explicit `force` still applies to the whole requested operation when policy permits.
- **Mutation authorization and audit semantics**: Non-exec mutation paths now use the normal high-risk approval/force semantics instead of implicitly forcing authorization. PTY session writes use line-buffered authorization for completed shell input, and session/forward/connection operations write operation-level audit entries.
- **Approval context risk details**: Daemon approval context now carries the effective risk produced by the authorization path, including trusted host overrides and matched approval policy names when available.
- **Desktop risk previews**: Desktop exec and session input previews now include host-level `risk_override` before prompting.
- **Remote daemon tag scope**: Client-side `remotes.toml` tag checks now read host tags from the remote daemon before forwarding, so tag-based remote scope decisions use the remote daemon as the source of truth.
- **Team config import semantics**: `config-import` now updates changed same-name hosts while preserving local key/password material, matching the existing import preview.
- **Policy compatibility**: Runtime policy loading now prefers unified policy files and falls back to legacy `risk_rules.toml` / `approval_policies.toml` when no unified policy exists.
- **Connection management**: Connection status/connect/disconnect now retain embedded SSH sessions instead of creating ControlMaster sockets; `socket_path` remains `null`.
- **Documentation**: README, architecture, OpenAPI, configuration, daemon quickstart, MCP quickstart, and plan docs now describe the completed G-stage control-plane capabilities and the exact PTY/session audit boundary.

### Fixed
- **Desktop mutation parity**: Desktop-local SFTP, session, forward, and connection operations now use the same high-risk approval/force semantics as daemon, CLI, and MCP paths.
- **Desktop operation audit**: Desktop-local session, forward, and connection mutations now append operation-level audit entries for success and failure.
- **Vite production chunks**: Production frontend builds now split terminal, React, UI, icon, and runtime vendor chunks without the previous large-chunk warning.
